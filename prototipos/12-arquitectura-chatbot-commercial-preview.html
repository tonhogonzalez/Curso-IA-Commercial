02 · Arquitectura de Doble Vía

¿Cuándo responde la Base de Conocimiento y cuándo entra el protocolo A2A?

Separar el conocimiento estático/normativo (RAG) de la operativa en tiempo real (Agentes Python A2A) evita alucinaciones sobre saldos o límites y permite escalar nuevos agentes sin tocar el asistente principal.

📚 Vía A · Base de Conocimiento (RAG Híbrido + Reranking)

LATENCIA MEDIA: ~650 ms
PASO 01 · INGESTA SEMÁNTICA POR DOCUMENTO

Manuales de producto (Confirming, Factoring, avales, tarifas) troceados respetando tablas y epígrafes con metadatos de vigencia y segmento (Pymes, MidCorp, Corporates).

🛰️ Vía B · Protocolo A2A → Agentes Operativos en Python

LATENCIA MEDIA: ~1.100 ms
PASO 01 · DESCUBRIMIENTO DE CAPACIDADES (/.well-known/agent.json)

El Orquestador consulta el registro de Agent Cards para localizar qué agente especialista expone la skill necesaria (p. ej. get_liquidity_position o simulate_credit_renewal).

PATRÓN 01 · 100% BASE DE CONOCIMIENTO

Preguntas de producto, normativa o ayuda de canal

No requiere consultar datos privados del cliente. El router activa únicamente el motor RAG híbrido y exige cita verificable.

«¿Qué diferencia hay entre Confirming con recurso y sin recurso?»
PATRÓN 02 · 100% DELEGACIÓN A2A OPERATIVA

Consultas sobre saldos, remesas, límites o estado de firmas

El Orquestador delega la tarea vía A2A al agente Python especialista propagando el token OAuth2 OBO del usuario.

«¿Qué facturas vencen esta semana en mi línea de descuento?»
PATRÓN 03 · EJECUCIÓN EN PARALELO (RAG + A2A)

Operativa contextualizada con condiciones contractuales

LangGraph lanza una rama `asyncio.gather` hacia la Base de Conocimiento y otra hacia uno o varios Agentes A2A y fusiona la respuesta.

«Si anticipo hoy 180.000 €, ¿qué coste tiene y cuánto límite me queda?»
03 · Interoperabilidad Entre Agentes

El Protocolo A2A (Agent-to-Agent) paso a paso

Mientras que MCP (Model Context Protocol) conecta un agente con sus herramientas o datos, A2A permite que el Agente Orquestador del Chatbot converse y delegue tareas complejas a Agentes Especialistas autónomos construidos por distintos equipos en Python.

1. Agent CardContrato JSON público en /.well-known/agent.json donde cada agente Python declara sus skills, esquemas de entrada/salida y autenticación.
2. Task & ContextUnidad de trabajo con task_id y session_id que pasa por estados trazables: submitted → working → completed (o input-required).
3. Message & PartsMensajes estructurados que combinan TextPart (instrucción natural) y DataPart (parámetros tipados como CIF, divisa o importe).
4. Streaming SSEMediante tasks/sendSubscribe, el agente Python emite eventos en tiempo real («Consultando CIRBE...») que la App/Web muestra al instante.
5. ArtifactsResultado final inmutable y validado con Pydantic v2 que el Orquestador transforma en texto o en tarjetas UI interactivas en la App.

      05 · Seguridad Bancaria por Diseño
      
Defensa en Profundidad: ningún Agente opera fuera de las atribuciones del cliente

      
Pasa el cursor por cada anillo o tarjeta para explorar las 5 capas de control entre la App/Web y el Core Bancario.

CORE
BANCARIO

      


      

        

          01
          
Propagación de Identidad On-Behalf-Of (OBO) + mTLSEl agente Python nunca usa una credencial genérica con acceso total: intercambia el JWT de la sesión Web/App por un token OBO acotado exclusivamente a las empresas y apoderamientos del usuario.

        

        

          02
          
Guardrails de Entrada/Salida y Enmascaramiento PIIFiltro en tiempo real contra Prompt Injection, jailbreaks y fugas de datos sensibles antes de invocar al LLM y antes de renderizar la respuesta en el canal.

        

        

          03
          
ACL Documental en RAG + Esquemas Estrictos en A2AEn la base de conocimiento cada chunk se filtra por segmento de cliente; en A2A cada payload JSON-RPC se valida con Pydantic v2 e incluye claves de idempotencia.

        

        

          04
          
Human-in-the-Loop (Firma en App o Escalado al Gestor)Las consultas e informes son inmediatos, pero cualquier disposición de fondos o contratación devuelve estado input-required y exige firma SCA en la App o validación del gestor.

        

        

          05
          
Trazabilidad End-to-End con OpenTelemetryCada turno registra trace_id, versión del prompt, documentos citados, agentes A2A invocados, latencia y hash de respuesta para auditoría interna.
